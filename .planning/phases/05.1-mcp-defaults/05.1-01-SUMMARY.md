# Phase 5.1: MCP defaults (decisions on the phase 5 open questions)

Decided 2026-10-29 (Jack via Chief of Staff, after PR #5 merged).

| # | Question | Decision |
|---|---|---|
| 1 | Auth: static bearer vs OAuth 2.1 | Keep the static `MCP_TOKEN` bearer (>= 32 chars). OAuth can come later. |
| 2 | Which receipt statuses count | `parsed` + `reviewed` by default. `needs_review` is excluded from totals and results unless the tool call passes `include_needs_review: true`. `uploaded`, `parsing`, `failed` never count. |
| 3 | Same server vs separate deployment | Keep serving MCP from the API server at `POST /mcp`. |
| 4 | Transport | Keep stateless Streamable HTTP with JSON responses only (no sessions, no SSE; `GET /mcp` is 405). |
| 5 | search_purchases matching | Keep case-insensitive substring match over item name, printed text and mapped product name. |
| 6 | spend semantics | Keep `receipts.total_cents` (tax included); groups also report tax and savings sums. |

## Implementation
- `repository.Scope{IncludeNeedsReview}`; every `QueryRepository` method takes it (filters carry it as
  `PurchaseFilter.Scope` / `SpendFilter.Scope`). `CountedStatuses` is now parsed+reviewed,
  `CountedStatusesWithReview` adds needs_review.
- All six MCP tools accept `include_needs_review` (boolean, default false; non-boolean is a validation
  error) and every result reports `counted_statuses`. Merchant resolution and summaries use the same scope.
- Tests: `TestIncludeNeedsReviewScope` (every tool, both values, bad type) and the scope section of
  `TestQueryRepository` (every repository method against Postgres).
- No migration.
