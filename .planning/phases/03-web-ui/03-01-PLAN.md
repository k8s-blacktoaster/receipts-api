# Plan 03-01: Mobile web UI

**Phase:** 3 - Mobile web UI
**Requirements:** UI-01 (single photo per upload), UI-02, UI-03, UI-04, UI-05, UI-06; held items from PR #2 QA
**Branch:** phase-03-web-ui

## Goal
From a phone on the VPN: pick member -> take photo -> upload -> watch status -> open the receipt
(image beside parsed fields) -> fix a line -> approve (reviewed). Plus re-extract and merchant rename.

## Design
- `internal/web`: html/template pages + `static/` (CSS, ~50 lines of vanilla JS), all via
  `go:embed`; no CDN, no SPA, no htmx (not needed). Routes at `/`, JSON API stays under `/api/v1`.
  - `GET /` -> `/receipts`; `GET /receipts` list with status badges + upload form;
    `POST /upload`; `GET /receipts/{id}` detail; `POST /receipts/{id}` save fields + items;
    `POST /receipts/{id}/approve`; `POST /receipts/{id}/extract`; `GET /receipts/{id}/image`
    (blob store, by the receipt's source document); `GET|POST /member` picker (cookie
    `receipts_member`); `GET /merchants`, `POST /merchants/{id}/rename`.
  - POST errors re-render the page with the real status code (400/404/409/415/503) and a banner.
  - Upload logic shared with `POST /api/v1/uploads` (`UploadHandler.Ingest`).
- Auth: none beyond member selection; VPN is the boundary (documented). Forms are same-origin
  POSTs; a SameSite=Lax cookie only holds the member id.
- HEIC: research says iOS Safari transcodes HEIC to JPEG when the file input's `accept` list is
  restricted and does not include HEIC; `image/*` is matched literally, so the safe choice is
  `accept="image/jpeg,image/png"` (camera button adds `capture="environment"`). Server detects
  HEIC/HEIF (ISO-BMFF `ftyp` brand) and returns 415 with guidance; decoding HEIC needs cgo/libheif,
  and the vision provider only takes JPEG/PNG anyway.
- Guards (held requirements):
  - Receipt/item/adjustment edits are 409 while `uploaded` or `parsing` (chosen over a version
    column: simpler, and a queued job would overwrite any edit). Re-extract first sets
    `uploaded` (`RequestReextract`), so edits after clicking re-extract are refused, not lost.
  - DELETE is 409 while `parsing`.
  - Stale threshold doc fixed to EXTRACTION_TIMEOUT_SECONDS + 60s (job timeout + 30s, grace 30s).
  - Queue: an enqueue for a receipt whose job is running sets a rerun flag, re-enqueued when the
    job ends (re-extract after a lost claim requeues immediately).
- Merchant rename: normalized key; collision -> 409 naming the existing merchant (no merge in v1).
